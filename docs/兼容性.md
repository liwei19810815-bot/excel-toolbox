## 关于 Excel 2021

2021 和 2024 **都是 16.0**，这一点决定了绝大部分兼容性问题不存在：

| 风险项 | 2021 上的情况 |
|---|---|
| 版本判断逻辑 | `Val(Application.Version) >= 16` 对 2021 和 2024 结果相同，`CsvFormat()` 取到同一个值 |
| 类型库 / API 下限 | 代码用到的最高 API 是 2010 引入的（`customUI14`、`SparklineGroups`、`Databar.BarFillType`），2021 全部具备 |
| MSO 库符号 | 已全部改为本地常量副本 + 晚绑定，不存在编译期依赖 |
| **功能区图标** | **唯一需要实测的一项**，见下 |

### 图标是唯一真正需要在 2021 上验证的东西

`imageMso` 是 Office 内置图标 ID，各版本的图标集**可能**不同。
但换机这次提供了一个有力的数据点：

> 从 build 17928 换到 build 17932，重跑 `check-imagemso.ps1` 后
> **30 个图标的位图哈希一个字节都没变**，连占位图参照的哈希也一样。

这说明 16.0 各 build 之间图标位图是稳定的。**但这是证据，不是证明**——
17928 与 17932 只差 4 个 build，而 2021 与 2024 隔着好几年。

**所以交付到 2021 环境前，请在那台机器上跑一次：**

```bash
powershell -ExecutionPolicy Bypass -File "tests\check-imagemso.ps1"
```

它会输出总览图并重新生成本目录下的 `图标验收记录.md`。
把生成的哈希和本文件里的对比：**全部一致就说明 2021 的图标集与 2024 相同**，
有差异的那几个会被脚本直接判红并指出是哪个按钮。

> 这个检查存在的理由：`imageMso` 无效时 Excel 只是**静默不画图标**，
> 功能区照常加载、按钮照常能点、所有测试照样全绿——
> 用户看到的却是一排空白按钮。这类失败必须专门断言。

## Excel 版本下限是怎么定的

不是拍脑袋，是按代码里实际用到的 API 反推：

| API / 特性 | 引入版本 | 用在哪 |
|---|---|---|
| `customUI14` 命名空间 | **2010** | 功能区。这是硬下限——2007 只认 2006 版命名空间，选项卡根本加载不了 |
| `SparklineGroups` | 2010 | `modViz.AddSparklines` |
| `Databar.BarFillType` / `NegativeBarFormat` | 2010 | `modViz.AddDataBars` |
| `AddColorScale` / `AddIconSetCondition` | 2007 | `modViz` |
| `ExportAsFixedFormat`（PDF） | 2007 | `modFileBatch.ExportSheets` |
| `xlOpenXMLWorkbook` / `xlOpenXMLAddIn` | 2007 | 构建与导出 |

所以下限 = **Excel 2010**。

### MSO 库常量：同一个坑的第二种形态

`msoFileDialogFolderPicker`、`msoAutomationSecurityForceDisable`，以及
`MsoAutomationSecurity` / `FileDialog` 这类**类型声明**，都属于
**Office 共享库（MSO）**，不属于 Excel 类型库。

目标宿主的 VBA 工程一旦没有引用 MSO 库，这些符号在编译期就解析不了，
后果同样是**整个工程编译不过**。

**运行时探测救不了这件事**——`modCaps` 是运行期行为，而符号解析发生在编译期，
工程根本轮不到跑起来。

已改为 `modIO` 里的本地常量副本 + `Dim dlg As Object` 晚绑定：

```
MsoFileDialogType:     Open=1, SaveAs=2, FilePicker=3, FolderPicker=4
MsoAutomationSecurity: Low=1, ByUI=2, ForceDisable=3
MsoTriState:           msoTrue=-1, msoFalse=0, msoCTrue=1
```

> **`msoTrue` / `msoFalse` 最容易漏**。它们长得像语言内置的 `True`/`False`，
> 实际是 MSO 符号，而且取值不一样（`msoTrue = -1`）。
> 用在 `Shapes.AddPicture`、`Format.Line.Visible`、`LockAspectRatio` 这些地方。
> 第一轮清理 MSO 依赖时就漏掉了这四处，以为已经清干净了——
> 查的时候不要只搜 `msoFileDialog` / `msoAutomationSecurity` 这类"看起来像常量"的名字，
> 要搜 `\bmso[A-Z]` 把整个前缀扫一遍。

### 差点被一个常量顶到 2016

`xlCSVUTF8` 是 **Excel 2016** 才加进类型库的。在 2010/2013 上这个符号不存在，
后果不是"导出 CSV 用不了"，而是**整个 VBA 工程编译不过、59 个命令一个都加载不了**。

已改为字面量 `62` + 运行时版本判断（`modFileBatch.CsvFormat`），
2016 以下退回本地编码的 CSV。

> **新增代码时务必留意**：引用一个高版本独有的内置常量，代价是整个加载宏在低版本上全废。
> 拿不准就用字面量加运行时判断。

## WPS：本机实测不可用

用 `tests\probe-wps.ps1` 在本机 WPS 上实测（WPS 版本 12.10.x）：

```
Path              : D:\PROGRA~3\WPSOFF~1\...\office6
Name              : Microsoft Excel      ← 注意，它自称 Excel
Version           : 12.0
打开 .xlam        : 可用
VBProject         : 不可用（返回 Null）
Application.Run   : 失败 0x800A03EC
AutomationSecurity: 可用
SparklineGroups   : 可用
FileDialog        : 可用
```

**加载宏文件本身能被打开，但里面的 VBA 一行都跑不了。**
`VBProject` 返回 Null 且 `Application.Run` 直接失败，指向同一个原因：
这台机器的 WPS **没有可用的 VBA 宏引擎**。

WPS 多数版本的 VBA 宏支持需要单独安装金山的 VBA 组件，且要在
WPS 的信任中心里允许宏。**没有这一层，任何 VBA 工具箱都无法在 WPS 上运行**——
这与本工具箱的实现无关。

### 要在 WPS 上用，先做这两件事

1. 给 WPS 安装 VBA 宏组件，在 WPS 里确认能运行一个最简单的 `MsgBox` 宏；
2. 然后重跑 `tests\probe-wps.ps1`，它会输出一份能力矩阵，据此再决定哪些命令要标为不可用。

在第 1 步做到之前，**不要把 WPS 列进支持范围**。

## WPS 安装后会接管 Excel 的 COM 注册

这件事会直接影响开发和 CI，必须知道：

```
HKCU / HKCR  CLSID{00024500-0000-0000-C000-000000000046}\LocalServer32
    = D:\...\WPSOFFICE\...\office6\et.exe /Automation
Excel.Application\CurVer = Excel.Application.12
```

装了 WPS 之后，`New-Object -ComObject Excel.Application` 拿到的是 **WPS**，
连带版本号的 `Excel.Application.16` 也一样被劫持。

**而且 WPS 自称 `Microsoft Excel`**，只有 `Application.Path`（含 `WPSOFF…`）和
`Application.Version`（12.0）能认出它。

后果：构建脚本和回归测试会在毫不知情的情况下驱动 WPS 跑，
产出的 `.xlam` 和"全绿"的测试结论全是错的靶子。**跑错宿主还全绿，比直接报错危险得多。**

### 已做的防护

- `build\_ExcelHost.ps1` 提供 `New-RealExcel`，所有构建和测试脚本统一从它创建实例；
  拿到的是 WPS 就**直接报错中止**，并提示如何恢复。
- `tests\probe-wps.ps1` 用反向判据：拿到真 Excel 反而报错，提示需要先让 WPS 接管。
- 两者共用同一个 `Test-IsWpsHost`，避免两边各写一套判据、各错一半。

### 判据的坑：8.3 短路径

WPS 的 `Application.Path` 返回的是 **8.3 短路径** `D:\PROGRA~3\WPSOFF~1\...`。
用 `"WPSOFFICE"` 去匹配 `"WPSOFF~1"` **匹配不上**——第一版修复就栽在这里，
改完自以为修好了，实跑才发现仍然认不出来。

现在路径判据统一用 `WPSOFF` / `KINGSO` 这样的短名前缀，
并以版本号（< 14）作为第二道判据。

### 恢复 Excel 为默认自动化宿主

> WPS → 设置 / 配置工具 → 兼容设置 → 取消 Office 文件关联，
> 或点「恢复 Office 默认设置」

建议平时让 Excel 拿着 COM 注册，只在需要验证 WPS 时临时切过去。

## 宿主能力运行时探测

`modCaps` 在运行时直接问宿主"你有没有这个能力"，不支持的命令在功能区里**灰显**，
而不是等用户点了才报错：

| 能力 | 探测方式 | 影响的命令 |
|---|---|---|
| 迷你图 | 只读取 `Range.SparklineGroups.Count` | `viz.sparklines` |
| 文件夹对话框 | 取 `Application.FileDialog` 对象（不 Show） | `merge.folder`、`file.*` |
| AutomationSecurity | 只读该属性 | `merge.folder`（**安全前置**，拿不到就停用） |

探测一律**只读**——为了知道"能不能加数据条"就真去加一条再删掉，
会弄脏用户的表、破坏撤销栈，代价远大于收益。

这比在 `clsActionDef` 上人工维护一张"哪个宿主支持哪个 API"的表可靠得多：
那张表在开发机上根本没法验证，事实上在本项目里也一直是空的
（59 个命令没有一个标过 `SupportedInWps`，所谓"WPS 下自动灰显"从来没生效过）。

## 语言与区域：本期只交付中文版

v1.0.0 是**中文版**：界面文案、结果消息、生成的报告表头全部是中文，
并且假定运行在**中文区域设置**的机器上。英文/海外版（系统 + Office + 时区全套）
作为下一期单独迭代。

### 已经做对、不必返工的部分

| 项 | 说明 |
|---|---|
| `Range.Formula` | 用的是 `.Formula` 而非 `.FormulaLocal`。前者永远是美式英文函数名，与 Excel 界面语言无关，`=IFERROR(...)` 在任何语言版本都写得进去 |
| `Range.NumberFormat` | 同理，用 `.NumberFormat` 而非 `.NumberFormatLocal`，`"yyyy-mm-dd"` 各语言版本通用 |
| 功能区 | `imageMso` 是语言无关的内置图标 ID；`customUI14` 命名空间、`xl*` 常量都是数值 |

**结论：英文界面的 Excel 上，本工具箱能正常工作，只是菜单是中文的。**
这是本地化问题，不是兼容性问题。

### 下一期必须处理的（现在是真缺陷，只是中文区碰不到）

1. **小数点分隔符** —— `modStr.NormalizeNumericText` 无条件 `Replace(buf, ",", "")`，
   把逗号一律当千分位删掉。在德/法/西等**用逗号作小数点**的区域设置下，
   `1,5`（一点五）会变成 `15`，`CDbl` 照单全收。
   **静默算错 10 倍，不报错、不标记**。
   正确做法是读 `Application.International(xlDecimalSeparator)` 再决定怎么清洗。

2. **日期顺序** —— `modUtils.TryParseDate` 末尾回退到 `IsDate` / `CDate`，
   这两个跟随 Windows 区域设置：`3-4-2024` 在 en-US 是 3 月 4 日，在 en-GB 是 4 月 3 日。
   （8 位纯数字和中文年月日已经用 `DateSerial` 显式处理，不受影响。）

3. **界面文案外置** —— 59 个标签 + 59 条说明 + 全部结果消息 + 报告表头
   抽成资源模块。工作量中等但纯机械。
   **注意**：不要用 `Application.LanguageSettings.LanguageID` 来判断语言——
   那是 MSO 库符号，会引入编译期依赖（同本文档「MSO 库常量」一节）。
   用 `Application.International(xlCountryCode)`，它属于 Excel 库。

4. **中国特有功能的去留** —— 金额大写、身份证解析、提取中文在海外版是噪音，
   需要决定是隐藏还是保留。

### 时区：已确认不是风险

全工程只有四处取当前时间，都不做跨机器比较：
`clsUndoTx.CreatedAt`（仅本会话内）、文件清单的 `DateLastModified`（仅显示）、
`modUtils.AgeFrom` 用 `Date` 算年龄（跨时区最多差一天，且身份证本就是中国场景）、
`modLoader` 用 `Format$(Now,"hhnnss")` 拼临时文件名（仅去重）。
自动更新的版本比对走的是版本号和文件大小，不依赖时间戳。

### 部署约束

**本期交付的 .xlam 不要装到非中文区域设置的机器上**——
不是不能用，而是第 1 条会静默算错数字。海外机器等下一期。
