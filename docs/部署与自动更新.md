# 部署与自动更新（内网）

目标：同事**打开 Excel 就能用，升级不需要做任何操作**。

---

## 架构

```
共享目录（只有维护者可写）              每台机器
├─ manifest.txt          → 1.2.0        ExcelToolboxLoader.xlam    瘦加载器，装一次永不变
├─ ExcelToolbox_1.1.0.xlam                    │
└─ ExcelToolbox_1.2.0.xlam  ← 发版新增         ↓ 启动时按清单拉取
                                        %LOCALAPPDATA%\ExcelToolbox\
                                        └─ ExcelToolbox_1.2.0.xlam  本地缓存
```

加载器只做三件事：读清单 → 缺了就从共享盘复制到本地 → 打开本地那份。
**59 个命令全在载荷里**，功能区也来自载荷——所以连按钮改动都能随版本下发，不用碰客户端。

### 为什么不直接让大家链到共享盘上的 .xlam

Excel 加载加载宏时会**占住文件锁**。只要公司里有一个人开着 Excel，你就覆盖不了那个文件。
几十个人的环境里，这等于永远没有发版窗口。

版本化文件名把"覆盖"变成"新增"，锁的问题根本不存在。

### 为什么要复制到本地再打开

1. 直接打开共享盘上的载荷同样会锁住它，旧版本就删不掉了；
2. 共享盘一断，所有人的工具箱当场失效。有本地缓存，出差、VPN 掉线照样能用。

### 并发：几十个人同时开 Excel

这不是边缘场景，是每天早上都会发生的事。两处专门为它做了设计：

- **临时文件名带进程 ID 和随机数**。固定用 `<版本>.part` 的话，A 正在写、B 一上来就把它删了重写，
  两边再交错改名，最后谁也说不清缓存里那个文件是完整的还是拼出来的。
- **改名失败不算错误**。并发时另一个进程可能刚好已经放好了同一个版本——
  这时候检查目标文件是否完整，完整就直接用，等于别人替我们干完了。
  也**不会先删目标再改名**：删掉会制造一个空窗，让第三个进程读到"文件不存在"。

打开之前还会校验载荷**可独占打开且大小合理**，一次挡掉三种情况：
别的进程正在写、上次复制中断的半截文件、被杀毒软件锁住。
校验不过就退回上一个缓存版本——总比打开一个坏文件强。

### 发布为什么先放载荷、最后才改清单

顺序反了会出现一个致命窗口：清单已经指向新版本，载荷却还没复制完，
这期间启动 Excel 的同事会去拉一个半成品。

`publish.ps1` 的顺序是：上传到唯一临时名 → 校验大小一致 → 原子改名为最终名 → **最后**更新清单
（清单本身也是临时文件+改名替换）。

这保证了一条不变式：**清单指向的版本，一定已经完整可用。**

原子性的边界说清楚：临时文件和最终文件**在同一个目录**，所以 `Move-Item` 是一次重命名而不是
跨卷复制，不存在"改名改到一半"的中间状态。这条保证止于 SMB 服务器端的文件系统——
NTFS 上成立。如果把发布目录放在不保证原子重命名的存储上（某些 NAS、同步盘、对象存储网关），
需要另行评估。发布脚本在改名后还会再核对一次文件大小，不只依赖"没抛异常"。

### 载荷完整性怎么判断

只看**文件大小**，不去打开文件探锁。

原本这里用 `OpenTextFile` 试探"有没有被别人占用"，那是错的：FileSystemObject 根本没有
独占打开模式，打得开只说明能按文本读；更糟的是反方向——同事开着两个 Excel 窗口是常态，
第一个已经打开了载荷，第二个来探测就可能失败，于是把一个**完好的缓存**判成不可用，
最后弹出"无法启动"。

而"半截文件"这个担心在本设计里本来就不成立：复制走的是唯一临时名 + 改名，
最终文件按构造要么不存在、要么完整。发布目录可达时用源文件大小做权威比对，
不可达时只做下限检查——宁可放行，也不能让出差的同事用不了工具箱。

### 加载器为什么是无状态的

它**不记录**"已安装哪个版本"，而是直接扫缓存目录看有什么文件。

记录会和实际对不上：记录说装了 1.2.0，文件却被杀毒软件删了，加载器就会一直打不开、
还找不到原因。扫目录的做法自带自愈——文件没了就重新拉。

## 首次部署

### 1. 准备共享目录

建一个目录，权限设成：**维护者可写，其他人只读**。

> ⚠️ **能往这个目录写文件的人 = 能让全公司的 Excel 执行任意 VBA。**
> 这是整套机制最关键的一条，代码层面无法弥补，只能靠 ACL。
> 信息安全评审大概率会问到这一点，建议主动写进申请材料。

### 2. 构建并发布载荷

```bash
powershell -ExecutionPolicy Bypass -File "build/build.ps1"
```

```bash
powershell -ExecutionPolicy Bypass -File "build/publish.ps1" -SharePath "\\你的服务器\共享目录"
```

`publish.ps1` 会从 `modApp.bas` 的 `APP_VERSION` 读版本号，上传 `ExcelToolbox_<版本>.xlam`，
然后把清单指向它。**同一个版本号不允许重复发布**——已经拿到该版本的客户端不会再下载，
重复发布会导致同一个版本号在不同机器上内容不同，出问题根本无法追溯。

### 3. 构建加载器

```bash
powershell -ExecutionPolicy Bypass -File "build/build-loader.ps1" -SharePath "\\你的服务器\共享目录"
```

发布目录在**构建时写死**。这是刻意的：原本用注册表做运行时配置，但实测
Excel 宏里 `CreateObject("WScript.Shell")` 会被安全策略拦下（它是宏病毒的典型载体，
企业 AV 和 Windows ASR 规则普遍会阻止 Office 创建它），读取**静默失败**，
在同事机器上完全看不出来。发布目录本来也几乎不变，不值得为它引入一条随时可能被掐断的依赖。

### 4. 每台机器装一次加载器

把 `dist/ExcelToolboxLoader.xlam` 发给同事，或由 IT 用登录脚本推到
`%APPDATA%\Microsoft\AddIns\`，然后在 Excel 里勾选它（开发工具 → Excel 加载项）。

也可以用仓库里的脚本（需先完全关闭 Excel）：

```bash
powershell -ExecutionPolicy Bypass -File "build/install.ps1" -OutputName "ExcelToolboxLoader.xlam"
```

### 5. 把本地缓存目录加进受信任位置

> Excel → 文件 → 选项 → 信任中心 → 信任中心设置 → 受信任位置 → 添加新位置
> 路径：`%LOCALAPPDATA%\ExcelToolbox`

**不做这一步，每次启动都会弹宏安全警告，"无感"就破功了。**
IT 可以用组策略统一下发这个受信任位置。

## 日常发版

改完代码后：

1. 把 `src/code/Core/modApp.bas` 里的 `APP_VERSION` 递增
2. `build.ps1` → `verify.ps1` → 三个测试套件全绿
3. `publish.ps1 -SharePath ...`

**不需要通知任何人，也不需要任何人关闭 Excel。** 同事下次打开 Excel 时自动就是新版。

### 只让一个人发版

`publish.ps1` 已经处理了"发布失败时还原旧清单"，并且在还原前会确认清单**确实还是自己刚写的那份**——
两个人同时发布时，不会拿自己的旧备份把别人成功的发布回滚掉。

但这只是兜底。**发版这件事本身应当串行**：约定只有维护者一个人发，
或者在共享目录上用一个简单的锁文件约束。并发发布是运维纪律问题，不是代码能彻底解决的。

### 回滚

线上出问题时，把清单改回上一个版本号即可：

```bash
powershell -ExecutionPolicy Bypass -File "build/publish.ps1" -SharePath "\\..." -Version 1.1.0 -Rollback
```

客户端下次启动自动退回，**不需要碰任何一台机器**。
这也是加载器按"清单说了算"而不是"版本号更大才更新"来判断的原因。

---

## 生效时机

新版本在**下次打开 Excel 时**生效，做不到会话中途热更新——
加载宏无法在运行中替换自己，这是 Excel 的硬限制。

所以"无感"的准确含义是**用户不需要做任何动作**，不是"立刻生效"。

## 排障

在 Excel 里按 Alt+F8，或在 VBE 立即窗口执行：

```vba
?Application.Run("'ExcelToolboxLoader.xlam'!Loader_Status")
```

输出示例：

```
share=\\fs01\tools\ExcelToolbox|shareReachable=True|remote=1.2.0|cached=1.2.0|active=1.2.0|cacheDir=C:\Users\xxx\AppData\Local\ExcelToolbox|payloadOpen=True
```

| 字段 | 含义 |
|---|---|
| `shareReachable` | 能否访问发布目录。False = 网络或权限问题 |
| `remote` | 清单里写的版本。空 = 连不上，或清单内容非法被作废 |
| `cached` | 本地缓存里最新的版本 |
| `active` | **当前真正加载的版本** |
| `payloadOpen` | 载荷是否已加载。False = 工具箱不可用 |
| `lastUpdate` | **最近一次更新的结果**。`ok:<版本>` = 正常；其余是失败原因（连不上发布目录、清单非法、复制失败、文件被占用…） |

强制立即重新检查（不用重启 Excel）：

```vba
?Application.Run("'ExcelToolboxLoader.xlam'!Loader_CheckNow")
```

### 常见情况

| 现象 | 原因 | 处理 |
|---|---|---|
| 没有"工具箱"选项卡，也没报错 | 缓存目录不在受信任位置，载荷的宏被禁用 | 加受信任位置 |
| `remote` 为空但 `shareReachable=True` | 清单内容非法（版本号只允许数字和点） | 检查 `manifest.txt` |
| `active` 比 `remote` 旧 | 复制失败（权限/磁盘满） | 看 `cached`，手工复制一次试试 |
| 断网后仍能用 | 正常，用的是本地缓存 | 无需处理 |

## 安全设计说明（供信息安全评审）

| 关注点 | 设计 |
|---|---|
| 代码分发通道 | 仅内网共享目录，**不走互联网**，无任何外部下载 |
| 写权限即执行权限 | 共享目录 ACL 必须限制为维护者可写，这是唯一的信任根 |
| 清单注入 | 版本号必须匹配 `N.N` / `N.N.N` / `N.N.N.N`，每段 1–4 位数字，不合格整条作废。杜绝用相对路径让加载器去别处取文件，也避免超长数字段导致的数值溢出 |
| 半截文件 | 复制先写带进程 ID 的唯一临时名再原子改名；打开前还会校验可独占打开且大小合理。中途断网、并发写入、被杀毒锁住都不会留下可被加载的残缺文件 |
| 发布窗口 | 发布顺序是"载荷就位 → 校验 → 最后改清单"，保证清单指向的版本一定已完整可用；同一版本号拒绝重复发布，避免同版本在不同机器上内容不同而无法追溯 |
| 运行时配置 | **没有**。不读注册表、不用 `WScript.Shell`，减少被安全软件拦截和被篡改的面 |
| 打开外部文件 | 合并文件夹等功能打开他人工作簿时强制 `AutomationSecurity = ForceDisable`，并**回读确认生效**；设不上就直接不打开该文件（计入失败清单）。这挡住的是 `Workbook_Open` / `Auto_Open` 一类的**自动宏执行**，**不等于**对方文件完全无害——外部链接、DDE、嵌入对象等路径不在此开关覆盖范围内 |
| 不可撤销操作 | 文件重命名、导出、断开链接等执行前强制确认，并在结果里如实说明已完成的部分不会自动回退 |
